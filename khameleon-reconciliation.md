# Khameleon — Cowork ↔ Design-spec reconciliation

Full reconciliation between two documents that were built completely blind to each other: `Khameleon_v1_Scope.md` (written in a Cowork session, backed by three standalone modules — `khameleon-window-agent`, `khameleon-file-agent`, `khameleon-memory`) and `khameleon-design-spec.md` + `khameleon-decisions-log.md` (an independent, longer-running effort dating to 2026-08-07, with its own verified prototype). Read in full — all 377 lines of the spec, all 197 lines of the decisions log — before writing this.

## Headline finding: the two projects agree on the thing that matters most

`khameleon-design-spec.md` §2 ("Security and data architecture") and `Khameleon_v1_Scope.md`'s core positioning are, independently, the same idea: Khameleon orchestrates the tools a person already uses rather than becoming a new place their data lives — "no extraction, no shadow copy," "manipulation, not migration," permissions inherit from the underlying system. Neither document influenced the other. That convergence is a good sign, not a coincidence to paper over — it means the instinct behind everything built in this Cowork session was pointed the right way even without seeing the fuller spec.

## The one thing that needs checking before anything else: `khameleon-prototype/`

The decisions log references a `khameleon-prototype/` directory repeatedly and specifically — as the location of `server.ts`, `scheduler.ts`, `src/connectors/web.ts`, `electron/main.js`, `electron/webapps.js`, and `data/*.json` — and claims several of these were **verified live**, not just written: the Aug 12 entries describe a real HTTP server booting, a real scheduled cron run firing unattended and landing in history, and a real router→skill→confirm flow tested end-to-end.

**That directory does not exist anywhere in the current `KhameleonApp` folder.** I searched for it and found nothing. This matters a lot for answering "is it all built" honestly: the decisions log's verification claims may all be accurate, but I cannot currently confirm any of them, because the code they refer to isn't present on this machine. Possibilities: it lives in a separate Replit project that was never pulled down locally, it was consolidated into `artifacts/api-server` at some point and the log wasn't updated to reflect that, or it was deleted. Worth resolving before trusting the decisions log's "verified" claims at face value — right now they're unconfirmable claims, not confirmed facts, from where I'm sitting.

## Decisions already made elsewhere that our scope doc should inherit

- **Composio (a managed-auth connector platform) was evaluated and explicitly rejected** (2026-08-12) because self-serve OAuth tokens would live in Composio's cloud — a direct conflict with the same "nothing new to trust with your data" principle both documents share. Relevant if anything in future work considers a similar third-party connector platform.
- **Onboarding requirements are tracked as a running catalog** (§14) — display name/role, an Anthropic API key, Microsoft Graph credentials, app connections chosen at signup, schedule preferences. `Khameleon_v1_Scope.md` never addressed onboarding at all — a real gap in our own planning, not theirs, worth folding in.
- **Commercial-readiness caveats are already logged** (2026-08-12): auth/billing/secrets management, multi-tenant data isolation, a required security review, an AI-provider-ToS review before commercializing, and an explicit note that wake word / always-on background listening "needs a persistent background process; not buildable inside a Cowork session." That last point is a direct, prior confirmation of the same environment limitation this Cowork session has been running into with `khameleon-window-agent`'s native dependency — good convergent validation, not new risk.

## Branding: less of a conflict than it first looked

The design spec's own language never uses "Jarvis" — it consistently says "the orb," "Khameleon," "the assistant." The `JarvisOrb.tsx` / `useJarvis.ts` / `JarvisStubPage.tsx` naming in the actual code is leftover from before the 2026-08-24 `Nexus Command → Khameleon Command` rename, not a spec-level decision to keep JARVIS branding. The design intent already matches the "no JARVIS branding" guidance; the code just hasn't fully caught up to its own rename yet — a cleanup task, not a strategy disagreement.

## What this means practically

1. Treat `khameleon-design-spec.md` as the senior document for anything it already covers — window management (§6/§7), the agent/skill architecture (§11), web access (§13), and the security/data principles (§2). `Khameleon_v1_Scope.md`'s value going forward is mainly the commercial/competitive analysis (Grok Bot, market positioning) and the three verified modules, not a competing product spec.
2. Locate or rebuild `khameleon-prototype/` before trusting any of the decisions log's "verified live" claims about the Outlook skills, scheduler, or web-access features.
3. `memory.tsx`/`research.tsx`/`vault.tsx` need a direct read to know if they're functional or scaffolding — flagged here, not yet checked.
4. The four open DECISION items (#14–17) are still genuinely open in both documents — nothing found here resolves them. They still need an actual answer from you, not an inference from either document.
