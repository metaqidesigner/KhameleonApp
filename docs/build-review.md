# New Builds Review — Decisions

Newton's rule (2026-10-10): before any implementation, each new build is reviewed one at a time with a recommendation and alternatives. Source list: `docs/gap-review.md` → "New builds required." Every build targets the overlay UI first and is mirrored into the Classic (old dashboard) UI — see `DECISIONS.md`.

| # | Build | Decision |
|---|---|---|
| 0 | How the two UIs stay in sync | **One app, two layouts, shared logic.** Backend calls, data, settings and logic are written once and shared; only the views are built per layout. A setting switches Overlay ↔ Classic. Desktop app defaults to Overlay; a plain browser always gets Classic (a browser can't float a see-through layer over other programs). Every change checked against both layouts before push, with `docs/ui-parity.md` updated. Classic can be deleted later by removing its view files and the setting — shared logic is untouched. Open for later: what browser-only users get if Classic is ever removed. |
| 1 | The desktop app the overlay runs in | **Electron — extend the existing `apps/khameleon-shell`.** One full-screen, see-through window that sits on top of everything; only the toolbars, head and chat (when open) catch clicks, everything else passes straight through to the user's apps. Tauri rejected for now (full rewrite of the shell and window-agent work). Considered and rejected: a layer that sits *behind* the user's windows like wallpaper (calmer, but hidden whenever a window is maximised, and Windows has no official support for it), and a hybrid that stays behind until summoned. Kept the original always-on-top design because Khameleon has to be reachable while acting on what's on screen. |
| 2 | The overlay layout in the real app | **Small steps, only real parts.** Order: (a) overlay window in `apps/khameleon-shell` loading the real frontend, (b) toolbars wired to actions that already exist, (c) the real chat and head, (d) saved look choices (palette, top/bottom bar or icons, bare icons) plus the Overlay ↔ Classic setting. Each step pushed, mirrored into Classic where it applies, and shown to Newton before the next. Settings/Workspace/Skills icons say "coming soon" until their builds land — no empty panels. Rejected: whole shell at once with empty panels (repeats the old dashboard's fake-button problem); browser-first (can't float over apps or pass clicks through, so would be partly redone). |
| 3 | The three panels (Settings, Workspace, Skills) | **One panel at a time, in order of use: Skills → Workspace → Settings.** Each panel shows only tabs that already work; new tabs appear as their features are built — never an empty tab. Skills first (heart of the product): existing skills with run/edit/delete/import; procedure-comparison results arrive with the capture builds. Workspace next (Tasks with project grouping, Status with the merged activity log incl. failures + Undo, honest energy/model figures). Settings last (set-up-once; includes the Vault edit screen). Rejected: all three at once (too big to check across both layouts); Settings first (least-used, and Build 2 already saves look choices). |
| 4 | Capture (record a task → skill) | **Target: full click/keystroke recording (replayable) as the main method, snapshot capture as the backup, plus "Describe instead" (type/speak the steps) for users who'd rather not record.** Build order: snapshots + Describe first (works on Mac with the existing shell, weeks not months), then full recording layered on top — it becomes primary and snapshots become the fallback automatically; review screen, written steps and Skills panel are shared, nothing rebuilt. Safeguards for full recording: password-field keystrokes never recorded (logins come from the Vault); steps target named UI elements, not screen coordinates; during replay, if a step can't find its target, fall back to the snapshot (vision) or stop and ask — never guess. Always: visible border + "Recording" badge + Pause; snapshots stay local and are deleted once the skill is saved. Windows side of full recording needs real-Windows verification. |
| 5 | Procedure documents + comparison | **Step-by-step check with quoted evidence.** Work Domains hold procedure documents (PDF/Word/scan, via the existing document reader incl. offline OCR), added in Workspace → Domains & documents. Capture suggests a domain for each new skill; the skill's steps are then checked automatically against that domain's procedures. Each step is matched to a procedure passage; missing / extra / out-of-order / contradictory steps are flagged, and every flag quotes the procedure text it relies on. Result in the Skills panel: "Matches" / "Differs at step N" / "No procedure found", clickable for a side-by-side view. Documents can be marked confidential → compared on the existing offline model, labelled "less certain." Manual "Re-check" button kept; when a procedure document changes, its skills are re-checked automatically and flagged quietly. Rejected: single % score (not actionable or auditable); manual-only checks (drift goes unnoticed). |
| 6 | Automatic task detection | **All three methods, layered.** (1) Spot repeats: a private, local log of app/window switches only (no keystrokes, no screenshots); a sequence recurring on different days triggers one offer in the suggestion slot ("Capture it next time?"); "no" silences that pattern for good. (2) Procedure matching on top: ranks which repeats are worth offering and offers capture when activity strongly resembles a domain procedure. (3) Content watching last: a separate switch, off by default, with a visible "watching" indicator, Pause, per-app exclusions (banking, personal email) and a daily cost cap. Detection only ever *offers* — never captures by itself. Master switch in Settings, off by default. Built after Capture (4) and Procedure comparison (5) have seen real use; needs its own detailed plan before coding. |
| 7 | Skills use saved logins | **The skill names the login, asks before using it, and the AI never sees the password.** A skill stores a reference to a Vault item, never the secret. At run time Khameleon asks "Use your [name] login?" — *Once* or *Always for this skill*; a per-login "always ask" setting exists for the most sensitive accounts. The desktop shell types the secret directly into the login field, so it never reaches Claude. Every use goes to the Vault access log and the activity log. On a failed login the skill stops, names the login that failed and links to editing it in Settings → Credentials — no retries. Considered and rejected: ask-every-time only (tedious, leads to blind approval); passing the password to the AI (secret sent to the cloud); skip logins entirely and pause for the user (Newton chose unattended-capable skills). |
| 8 | Skills know their connections | **Fill the list automatically, check before every run.** Capture records which connected services the task touched into the existing `requestedIntegrationIds`. Skills panel shows connection badges (green connected / grey missing). Before a run, a missing connection prompts "This skill needs X — connect now?" and opens the connect screen directly, rather than failing mid-task. For desktop apps with no "connection" (Excel etc.), the check is "installed and open," with an offer to open it. Rejected: badges only (still fails mid-run); fail-and-explain (half-done tasks are messier than none). |
| 9 | Know which email is open | **Ask the app, fetch via the existing connection, screen reading as backup.** Gmail (browser): read the message id from the address bar, fetch via the Gmail connection. Outlook (Mac/Windows): ask the app for its selected message, fetch via the Outlook connection. Otherwise or on failure: screenshot + Claude identifies the email. Still unsure: the recent-messages picker. Safeguards: always name the chosen email before acting ("Replying to: …"), one click to switch to the picker. Uses the same Accessibility permission as Capture — no extra prompt. Rejected: screen reading only (slower, costs per click, less exact); picker only (extra step on the most-used actions). |
| 10 | Calendar in chat + meeting prep | **Chat gets a read-only calendar tool** over the existing Google/Outlook calendar fetch (`routes/calendar.ts`); creating/moving meetings deferred until asked for. **Meeting prep — all three:** (1) a short brief in the suggestion slot 15 min before meetings with other people (attendees, recent related emails, linked open tasks, notes from the last meeting with the same people), click to open in chat; skips solo blocks, focus time, declined meetings; lead time adjustable, switch-off in Settings. (2) Morning digest includes the day's briefs. (3) On request in chat ("prep me for the 3pm"). One brief per meeting, generated once and refreshed with any new emails before the 15-min reminder rather than regenerated from scratch. Cost ≈ one AI call per meeting. |
| 11 | Inbox in chat + urgent flags | **Chat gets a read-only inbox tool** backed by the existing triage classifier (reports only; sorts/archives only when asked). **Gmail version of the triage skill added** in this build, reusing the same classification logic (today triage is Outlook-only). **Urgent flags — default: check every 10 min**, flag only *urgent* mail from people the user actually corresponds with or has marked important; each flag says why; max 3/day by default, quiet hours (e.g. 7pm–8am), multiple flags grouped. **User setting to switch to** instant push alerts (only available when Khameleon is reachable from the internet, e.g. hosted mode — shown greyed with an explanation otherwise) **or** to flags off / on-request only. |
| 12 | Remaining small pieces | **(a) Past conversations:** clock icon in the chat header → last 30 conversations, auto-titled, searchable (reuses existing session-resume plumbing). **(b) Research auto-save:** results saved to memory automatically, tagged with topic + date, each with a "forget this" button. **(c) Parallel mode:** side-by-side answer cards in chat with "use this one"; agent picker shows a live status dot (working / idle / error). **(d) Starter-skill install button:** fixed. Task project grouping, merged activity log with failures + Undo, Vault edit screen and honest energy/model figures are covered by Build 3. |

## Review complete (2026-10-11)

Implementation order: Build 2 (overlay layout, steps a–d) → Build 3 (Skills panel → Workspace → Settings) → Build 12 pieces alongside the panels they live in → Build 4 (Capture: snapshots + Describe first) → Builds 8, 5 (connections, procedure documents + comparison) → Build 7 (saved logins, with full-recording replay) → Builds 9, 10, 11 (acting on open email, calendar, inbox) → Build 4 full recording → Build 6 (automatic detection, own plan first). Every step: overlay first, mirrored into Classic, `docs/ui-parity.md` updated, pushed.

Still open (not blocking): what browser-only users get if Classic is ever removed; mobile device control and terminal tools (undecided from earlier).
| 2 (addendum, 2026-10-12) | Idle look + multiple screens | **Idle:** toolbars fade to a faint outline (~25%) a few seconds after the pointer leaves them and return to full strength when the pointer nears an edge; the head always stays visible; Cmd/Ctrl+Shift+K hides everything. Edge auto-hide and always-visible offered as Look & layout choices; fade is the default. **Multiple screens:** Khameleon follows the user — the overlay moves to whichever screen the pointer settles on (short delay), with a setting to pin it to one screen. One set of toolbars, no duplicates. Capture/observe/control borders appear around the target window on whichever screen it's on. Folded into Build 2 step (b). |
| 13 (added 2026-10-12) | Projects you can tell apart at a glance | **Each project gets a short name and one of ~8 distinct colours, used everywhere that project's work appears:** a coloured chip on its chat conversation (switching project switches conversation; replaces the never-populated "Thread" picker); the past-conversations list grouped/coloured by project; the border Khameleon draws around an app window it's working in for that project (pulse pattern still shows watching vs controlling, colour shows which project); small dots around the head for projects in progress (hollow = scheduled), hover for name/progress, click to jump to its chat; project colour on tasks (Workspace) and skills (Skills panel). Khameleon files new chats/tasks into the most likely project, one click to change. Work Domains stay as the broader folder projects sit inside. Colours readable on both palettes; >8 active projects add an initial on the dot; finished projects drop off the head but stay searchable. Rejected: domains only (too broad); a chat window per project (clutters the overlay); names without colours (no at-a-glance recognition). Built after Build 3. |
